FINDING 2/17  [Blocker] [missing-capability]  (raised by technical-half reviewer)
LOCATION: section_2_workflow.md WF-80/WF-81 (lines 689-690), step 17 (line 33); section_5_nfr_plan.md §25.6 (lines 574-591)
EXACT TEXT IN THE DOCUMENT:
**Verified → In Test** (retract) is permitted only while the allocation has not been reported, requires Unit Incharge authority and a reason, and archives the verified result as a revision.
PROBLEM:
A draft report freezes `txn_report_test.snapshot_json` at compile (step 17), but WF-81 says an allocation only becomes Reported "as a consequence of a report reaching Issued". So between compile and issue — which spans the Approving Authority's signature queue and, with WF-5 switched on, a payment hold of arbitrary length — the allocation is still Verified and WF-80 therefore permits it to be retracted to In Test and its readings changed. Nothing in §25.6 guards report issue against this: there is no rule that every allocation on a report must still be Verified at the moment of issue, no state or lock reserving an allocation to a draft report, and no re-check of the snapshot against live values. The system will happily issue a signed, numbered, ULR-bearing report containing values the tester has since revised, and the audit trail will show the revision as pre-dating the issue. This is the single most damaging integrity hole in the document.
REQUIRED FIX:
Drop the new allocation state; use machinery the document already has. (a) Add to §25.6: "DB-43 | A report cannot move to Authorised or to Issued if any allocation it covers is not in state Verified at that moment, or if any of that allocation's current results carries a `rev_no` higher than the one frozen in `txn_report_test.snapshot_json`. | Trigger on both the report-authorisation and the report-issue transitions, re-reading `txn_sample_test.state` and `txn_result.rev_no` (where `is_current`) for every row of `txn_report_test`, and raising an error naming the offending allocation and its report number." The authorisation checkpoint is the load-bearing one, because M8-42 allocates the report number and ULR, renders the file, computes the checksum and applies the signature all at authorisation. (b) Amend DB-21 and the `txn_report_test` row in §25.4 so that `snapshot_json` additionally freezes, per result, the `txn_result.id` and its `rev_no` — without this DB-43 has nothing to compare against, since rev_no is not a printed value. (c) Amend WF-80 to: "**Verified → In Test** (retract) is permitted only while the allocation has not been reported, requires Unit Incharge authority and a reason, and archives the verified result as a revision. Where the allocation appears on any report not yet Issued, the retraction automatically returns that report to Draft, marks its snapshot stale so it must be recompiled before it can be submitted for authorisation again, names the report number to the retracting user, and notifies the report writer and the signatory." Acceptance check: "Compile a draft covering a verified allocation, submit it for authorisation, then retract that allocation. The report drops back to Draft with its snapshot marked stale, the signatory is notified, and authorisation is refused until the report is recompiled." This reuses the PENDING_APPROVAL → DRAFT send-back transition already in the report state model, needs no new allocation state, and so leaves WF-4, WF-81, §9.2 and the original-plus-amendment case untouched. Optionally add an AC-level scenario in §27 mirroring the DB-43 acceptance check, since the existing AC table has no case for a result revised while a report is pending authorisation.
