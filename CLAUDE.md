# Claude instructions for this repository

## What this is

A Laboratory Information Management System for the silk testing laboratory at RSTRS
Dharmavaram (Central Silk Board). Two halves:

- `parts/` — the specification sources. `SPEC.md`, `BRIEF.md`, the two `.docx` files,
  `index.html` and `parts/appendix.md` are **generated — never edit them directly**;
  edit `parts/*.md` and rebuild.
- `app/` — the working application: the Limited Test path end to end (counter →
  bench → verification → signed PDF/UA certificate → public QR verification),
  plus amendment, administration, registers, and a first-run setup wizard.

## Setting up and running the application

```bash
cd app && node start.js
```

`start.js` is self-diagnosing: it installs packages, finds or explains how to install
PostgreSQL 16, creates the database, migrates, asks one question (practice data? —
say **y** for a demo), and starts both servers. Internal app: http://localhost:8787,
public verify: http://localhost:8788. Demo sign-ins: `lakshmi` (counter), `ravi`
(tester), `suma` (verifier), `incharge` (signatory), password `dvm`.

Needs Node 20+ and PostgreSQL 16. On macOS, PostgreSQL may need
`LC_ALL=en_US.UTF-8` to start. On Windows, connect via `PGHOST=localhost` with the
password chosen during the PostgreSQL installer (start.js handles this and caches it
in `app/.lims-db.json`).

`node start.js --check` verifies everything without starting servers.

## If you are helping a NON-TECHNICAL person set this up

That is a supported, expected use. Follow `app/FIRST-DAY.md` — it is the walkthrough
written for them. Speak plainly, one step at a time, no jargon; run the commands
yourself rather than asking them to type; after setup, walk them through the test
script in that file (one sample's journey, all four roles) and show them what they
should see at each step.

## Tests

```bash
cd app && npm test          # ~52 tests; server tests need PostgreSQL running
```

The two PDF/UA conformance tests skip loudly unless `VERAPDF=/path/to/verapdf` and a
Java 11+ `JAVA_HOME` are set — that is deliberate; do not silence the skip.

## Rebuilding the specification documents

```bash
npm install && bash build.sh && python3 lint_spec.py SPEC.md
```

All eight lint checks must report zero. `parts/appendix.md` is regenerated by the
build; `parts/research_*.md` and Appendix A are historical records — do not "fix"
their contents (including their CloudZoo mentions).

## Hard rules

- **Certificates are practice-only until the real signing credential is installed**
  (`LIMS_P12` / `LIMS_P12_PASSPHRASE`). The bundled key's own name says NOT FOR
  ISSUE. Never present a demo certificate as a real one.
- `txn_event` and `txn_reading` are append-only (database triggers enforce it).
  Never try to update or delete their rows; corrections are new rows.
- Readings are never overwritten; a correction is a new generation revising the old.
  An issued report is never edited; it is amended (superseded) or withdrawn.
- Number series are gap-free and continue the paper registers (WF-112). Never reset
  a series or invent an opening number — the first-run screen asks for the real ones.
- pg returns DATE columns as JS Dates: format dates with `to_char` in SQL, never
  `String(date).slice(0,10)` — this trap has bitten three times in this codebase.
- The stack is decided (SPEC §24.4): Node.js server-rendered, PostgreSQL 16, pdfkit +
  harfbuzzjs + `/ActualText` for the certificate path. Do not swap pieces casually;
  the choices carry measured evidence (see `app/README.md`).
