### 23.4 Poor connectivity and offline behaviour

The design rule is deliberately simple, and it is chosen to avoid the hardest class of software bug. **There is exactly one authoritative copy of the data, and it lives on the server inside the laboratory.** Staff computers are browsers on the laboratory network. They are not offline copies. So "offline" here means "the internet is down", not "the laboratory network is down".

| ID | Requirement | Detail | How we verify it | Priority |
|---|---|---|---|---|
| NFR-29 | These screens must work with **no internet at all**, because they only need the laboratory network: customer look-up, sample registration, label printing, sample acceptance and rejection, allocation to testers, result entry, verification, report generation, report printing, sample retention and disposal, equipment and calibration screens, stock screens, all registers and all reports. | Full function, no degraded mode, no warning banner beyond a small "offline — 4 items queued to send" indicator. | The cable-pull test of NFR-27. | [MUST] |
| NFR-30 | These features may be unavailable when the internet is down, and must fail gracefully with a plain message and an automatic retry: publishing a verification record, pulling bank or portal payment statements, sending SMS or email, requesting an Invoice Reference Number from the Goods and Services Tax (GST) Invoice Registration Portal, obtaining a trusted timestamp for a signature where one is applied at all (it is not, under the default recorded at OPEN-Q-T31), off-site backup upload. | Each shows "Waiting to send — will retry automatically", never an error dialog, and never blocks the user's next action. | Cable-pull test; check the outbound queue screen. | [MUST] |
| NFR-31 | Every outbound integration is a queued job with automatic retry using increasing delays (1 minute, 5, 15, 60, then hourly), a visible queue, a failure count, and a manual "retry now" button for staff. | Queue screen shows: what is waiting, since when, how many attempts, last error in plain words. | Cable-pull test, then reconnect and confirm the queue drains without human action. | [MUST] |

## 24. Recommended architecture and technology

### 24.1 The single most important architectural rule

> **The application must run completely and correctly on one ordinary server inside the laboratory, with no internet connection, for at least a full working week.** Every feature that needs the outside world — the public verification page, payment reconciliation, Invoice Reference Number requests, SMS, off-site backup — is an optional, queued, retryable outbound job. None of them may sit on the path a scientist takes to log a sample, enter a reading, or issue a report.

Everything below follows from that rule and from the site facts: the unit is next to the Government Cocoon Market at Regatipalli, it serves walk-in customers with same-day expectations, and district connectivity and power are not dependable.

| ARC-02 | Every outbound integration is implemented as a queued job with retry, a visible queue and a manual retry, per NFR-31. | [MUST] |

### 24.4 Technology stack

**These recommendations apply as written, and the two that mattered most are now decisions rather than recommendations.** The laboratory system is a standalone application, not a layer inside somebody else's package, so there is no existing language, framework or database it has to inherit. ARC-13 and ARC-14 record the two branches and which of them is operative. Decision 1, the stack, is stated immediately below. Decision 2, what the signature on a report has to achieve, is registered as an open question with a recommended default at OPEN-Q-T31, and this section builds to that default and states what it costs if the default is wrong.

**Decision 1 — the stack is Node.js with TypeScript, server-rendered, on PostgreSQL 16.** What decided it is this section's own rule: *anything the developer has not shipped before: reject*. One person maintains this system for years, in a district unit with no information-technology support, and the developer has shipped JavaScript and Node work and nothing else. A framework he would be learning on the job is a larger risk than any difference in library quality between the candidates — and larger than the one genuine weakness this choice carries, which is set out in the digital-signing row. The earlier text of this section left the language open and offered three frameworks the developer does not use; that is now closed. Everything downstream of the choice — the PDF and signing rows especially — was then built and tested rather than assumed, because a stack chosen for maintainability still has to be able to produce the document this laboratory issues.

| ID | Requirement | Priority |
|---|---|---|
| ARC-13 | **Not operative.** This rule provided for the case where the laboratory layer had to be built inside an existing accounting system — sharing its database, its login, its screens or its deployment — in which case that system's language, framework and database would have decided the stack, and this section's recommendations would have been overridden except for the PDF, signing and verification components. No such system exists at this unit, so the case does not arise and ARC-14 is the operative branch. The rule is kept, with its reasoning, because it becomes live again the moment anyone proposes housing this system inside another: if that is ever proposed, the stack question is reopened, answered in writing, and recorded in the ARC-06 configuration record **before** any code is written against it. | [MUST] |

**A correction, recorded against ARC-17.** Until this revision the PDF row above named **ReportLab with pyHanko on Python** as a pair meeting all three requirements. That recommendation is **withdrawn, because it was false.** Open-source ReportLab cannot produce tagged PDF at all: structure elements, structure-parent references, alternative text and marked-content emission are absent from its source, and automatic tagging is a feature of the commercial ReportLab PLUS product. Anyone who followed the recommendation would have discovered this after committing the document component to Python. What is true instead: pyHanko is an excellent signing library, ReportLab is a good generator of untagged PDF, and the pair does not satisfy NFR-70. It is recorded here rather than quietly edited away, because ARC-17 exists so that a wrong library choice costs one component instead of the whole system, and because a reader who was told something false is entitled to see it named.

**What it costs if OPEN-Q-T31 is answered the other way.** The rows above are built to that question's recommended default — a valid signature, not long-term validation — on the strength of a verbal answer from the Unit Incharge, which is recorded there as an assumption and not as a fact. If the written answer from the Quality Manager or NABL turns out to require long-term validation, the remedy is not a code change but a change of component: the signing implementation is replaced through the ARC-17 interface with pyHanko run as a command line off the report-issue path, its second runtime recorded as an ARC-06 exception with its own ARC-16 vendoring plan. Budget two to three developer-weeks, and a second dependency tree to patch for the life of the system. Nothing already issued becomes invalid: NFR-121 governs how the material is added afterwards, to a separate derived file, without altering one byte of the original. This is cheap to prevent and awkward to repair, so the written answer is a Phase 0 task (PLN-04, PLN-06), not a Phase 6 one.

**Why long-term validation could not sit on the report-issue path in any language.** Worth stating once here, where the technology is chosen, so that it is not later mistaken for a limitation of this stack. Long-term validation needs revocation evidence fetched from the certifying authority — an online certificate status response or a revocation list — and an RFC 3161 round trip to a timestamping authority. Both are calls outside the laboratory network, and M8-46 and NFR-32 forbid such a call on the path that issues a report, because a report must issue with the line down. So even on a stack whose libraries do it comfortably, long-term validation is applied **after** issue, from the outbound queue, under NFR-121. The language decides how that material gets applied, never whether it may sit on the issue path.

**Why this separation matters, in one paragraph the scientist should read.** The verification page is the only part of this system that strangers can reach. If it sits on the same machine as the laboratory's records, then every weakness in that page is a route to every customer's results, every price, and every telephone number. By putting it on its own small machine that holds nothing except "report number X is valid, and here is its fingerprint", the worst that a successful attack on the public page can achieve is to learn things that are already printed on certificates people are carrying around the market. It also means the verification page keeps answering when the laboratory's power is off, and that the security audit needed before a Government-domain page goes live covers one small page instead of the whole system.

| ID | Requirement | Priority |

### 24.10 A plain-language note for the scientist: on-premise or cloud?

On-premise means the computer that holds your laboratory's records sits inside your building, where you can see it, and the software keeps working when the internet line fails — which at Dharmavaram it will. Cloud means those records sit in a data centre in Mumbai or Hyderabad, somebody else looks after the hardware, and you pay a monthly rent instead of buying a machine once — but when the line is down, the laboratory stops. My recommendation is the middle path: the working system lives on one small server in your laboratory, so sample login, testing, verification and report printing never depend on the internet, and only three things ever reach outside — the public report-verification page, payment confirmations from the bank, and the encrypted nightly backup. On cost, that means roughly one capital purchase of a server, a mirrored pair of disks, a third separate disk inside the server that holds nothing but the backups, one external disk that is swapped every week and taken off the premises, an uninterruptible power supply, a laser printer, a label printer and two scanners, plus a very small recurring charge for the little internet host that answers QR scans — instead of a cloud subscription that has to be sanctioned again every year. On control, it means the records are physically in Central Silk Board's custody at Dharmavaram, which is the easier position to defend to an internal auditor, to CSTRI headquarters and under the data-protection rules — and because the software is deliberately built not to depend on any one vendor, the same system can be lifted onto a Government-approved cloud later without being rewritten.

## 25. Database design

Naming follows the research pack: `mst_` for master (reference) data, `txn_` for transactions, `sys_` for system and platform tables. Every table has a machine-generated primary key called `id`. Human-readable numbers (sample number, report number, invoice number) are separate columns with a uniqueness rule — **never** the primary key.

Types are written in a portable form. `TIMESTAMPTZ` means "a moment in time stored in Coordinated Universal Time"; on MySQL or MariaDB use `DATETIME(3)` with the application guaranteeing UTC. `DECIMAL(p,s)` means an exact decimal number with `p` total digits and `s` after the point.

### 25.5 Cross-cutting design rules

| ID | Requirement | Priority |
|---|---|---|
| **DB-01** | **Every table** carries `created_at TIMESTAMPTZ NOT NULL`, `created_by_user_id BIGINT NOT NULL`, `updated_at TIMESTAMPTZ`, `updated_by_user_id BIGINT`. These are set by the application service layer, never left to the caller, and never editable through a screen. | [MUST] |
| **DB-02** | **Delete policy. There are no hard deletes in any `txn_` table, in `sys_audit_log`, in `sys_state_transition`, in `txn_custody_event`, or in `txn_observation`.** The application's database login is granted no DELETE permission on those tables. Withdrawal, cancellation, rejection and abortion are **states**, each with a mandatory reason. Master tables may carry `is_active` and, for genuinely wrong entries never used, `is_deleted BOOLEAN` plus `deleted_at`, `deleted_by_user_id`, `delete_reason`; deletion is refused if the master row is referenced anywhere. A voided record remains queryable and printable, watermarked VOID. | [MUST] |
| **DB-03** | Nothing is ever removed to "clean up". Retention is handled by `sys_retention_policy` with a proposal, a named authoriser and a permanent disposal record. No scheduled job may issue a DELETE against a technical record. | [MUST] |
| **DB-04** | **The audit log design.** One table, `sys_audit_log`, written by **database triggers** on every audited table, so that a change made by any route — the application, a maintenance script, or a person with a database client — is recorded. Columns: `id BIGINT`, `unit_id`, `entity_type VARCHAR(40)`, `entity_id BIGINT`, `action VARCHAR(20)` (insert, update, delete-attempt, state_change, login, print, export, download, permission_denied, unblind), `field_name VARCHAR(60)`, `old_value TEXT`, `new_value TEXT`, `changed_by_user_id`, `changed_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `reason_id`, `reason_text TEXT`, `ip_address VARCHAR(45)`, `session_id VARCHAR(60)`, `request_id VARCHAR(40)`, `source VARCHAR(20)` (application, script, direct), `row_hash CHAR(64) NOT NULL` — a SHA-256 taken over this row's own content together with the `row_hash` of the row before it, so the table forms a chain that the verification job of M21-31b re-computes end to end and can therefore prove that no row was altered or removed by any route. One row **per changed field**, not one per record, so that a change history reads as a list of specific changes. Indexes: `(entity_type, entity_id, changed_at)`, `(changed_by_user_id, changed_at)`, `(changed_at)`. Partitioned or archived by month once it grows. **Privileges, per M21-31: the application's database account has INSERT and SELECT only. UPDATE, DELETE, TRUNCATE, ALTER and DROP are revoked, together with the right to create, alter, disable or drop a trigger on the table, and the audit tables are owned by a separate database account that the application cannot authenticate as.** A guard trigger raises an error on every such operation a trigger can intercept and writes a `delete-attempt` row naming the account and the statement, so a blocked attempt is itself evidence; the operations no trigger can intercept are prevented by the grant model and the ownership, and the refusal surfaces through the database error log in the daily health digest (ARC-35). `reason_text` or `reason_id` is **NOT NULL for updates to** raw readings, results, methods, equipment status, competency authorisations, rate cards and any numbered document. | [MUST] |
| **DB-05** | The application sets the current user identity in a database session variable at the start of every request, so triggers can record `changed_by_user_id` without the application passing it into every statement. A write with no session user set is refused. Exactly one reserved non-interactive principal exists: the **scheduler account**. It has its own database role, its own `sys_user` row with `is_service_account = true`, `personnel_id` NULL, no password and no interactive login, and it cannot be granted any role that authorises, verifies, signs or issues. Scheduled jobs and the queue worker set the session user to that account, so their writes satisfy DB-01 and are attributed in `sys_audit_log` with `source = 'script'`. Any other connection that writes with no session user set is refused and the refusal is written to the database error log, which the daily health digest (ARC-35) surfaces. | [MUST] |
| **DB-06** | **The revision pattern for results.** `txn_result` holds one current row per (test, parameter) enforced by a partial unique index on `is_current`. Every change writes a `txn_result_revision` row holding the old and new values, the actor, the time and a mandatory reason, and increments `rev_no`. The raw readings in `txn_observation` are never updated: a correction is a **new observation row** whose `supersedes_observation_id` points at the old one, and the old one gets `is_excluded = true` with a reason. Both remain visible. | [MUST] |
| **DB-07** | **The revision pattern for reports.** An issued report row and its stored file are append-only. A correction is either an **amendment** (a new report row with `amends_report_id` set, carrying the literal statement "Amendment to Report, serial number X") or a **replacement** (a new report row with `supersedes_report_id` set, and the old row's `superseded_by_report_id` set). The original row is never updated except to set `superseded_by_report_id` and `state`, and those two updates are the only ones the database permits, enforced by a trigger. A machine-generated change list between the two versions is stored and printable. | [MUST] |
| **DB-08** | **Numbering: how to stop two clerks getting the same number.** The counter lives in `mst_numbering_counter`, one row per unit, document type, period and scope. Allocation runs in **its own short transaction**: lock the single counter row (`SELECT last_number FROM mst_numbering_counter WHERE ... FOR UPDATE`), increment it, commit. The number is then used in the business transaction. Because the counter row is locked, a second clerk's request waits a few milliseconds and gets the next number. **The following are forbidden and must not appear in the code:** `SELECT MAX(number) + 1` (two clerks read the same maximum and both get the same number); a database sequence (sequences leak numbers on rollback, and cannot be reset per financial year under control); generating any number in the browser or on a tablet. If the business transaction that was to consume the number fails, is abandoned or is lost to a server restart, the number is not reused: a `sys_number_void` row is written with reason `allocation not completed`. A reconciliation job runs at server start-up and nightly, finds every number at or below `last_number` with neither a document row nor a `sys_number_void` row, writes that row automatically, and records its outcome in `sys_job_run`. The Series Register therefore reports Missing only for a real defect, and the alert of DB-10 stays meaningful. | [MUST] |
| **DB-09** | **Numbers are allotted at the moment of issue, immediately before the transaction that commits the document, by the mechanism of DB-08 — never when a user opens a "new" form.** Otherwise abandoned drafts consume numbers. A draft shows "Not yet numbered". | [MUST] |
| **DB-10** | An allotted number is **never reused**. If a document is cancelled, its number is retired and a row is written to `sys_number_void` recording who voided it and why. A **series register report** lists every number from 1 to the current counter with its state — issued, cancelled, or **missing** — and any "missing" row raises an alert, because it means a bug. This is the software form of the General Financial Rules requirement to account for every form in a receipt book. | [MUST] |
| **DB-11** | For tax documents, the series definition enforces the Central Goods and Services Tax Rules, rule 46(b): at most **16 characters**, only letters, digits, hyphen and slash, consecutive, unique for the financial year. The system **refuses to save a series definition whose maximum possible number would exceed 16 characters.** Sample numbers, report numbers and Unique Laboratory Report numbers are not tax documents and are not subject to the 16-character limit. | [MUST] |
| **DB-12** | The financial year for a number is derived from the **India Standard Time date**, not the stored Coordinated Universal Time date. A document created at 04:00 IST on 1 April is 22:30 UTC on 31 March, and must land in the new financial year. This is a real and easily missed defect. | [MUST] |
| **DB-13** | The Unique Laboratory Report number is produced by a **template engine reading `mst_ulr_config`**, never by joining strings in code, because the format changed in June 2026 and the unit may be mid-transition. The running number is per calendar year, allotted atomically by the same mechanism as DB-08, and **only at the moment of report authorisation.** A draft report has no such number. | [MUST] |
| **DB-14** | **Attachments are files on disk or in object storage, with metadata in `sys_attachment`. Binary content is never stored inside a database row.** The reasons: photographs at 15 GB a year would make the database backup unusably slow and the restore-time objective unachievable; a database restore would then be an all-or-nothing operation; and streaming a 5 MB PDF out of a table wastes memory on a 16 GB server. Path layout: `/<unit>/<year>/<month>/<entity_type>/<id>/<uuid>.<ext>`. The stored name is a generated identifier, never the user's file name. Every attachment stores a SHA-256 fingerprint, verified weekly (NFR-42); where a derived long-term-validation copy of a report exists (NFR-121) it is a separate `sys_attachment` row with its own fingerprint and is verified as an independent row, and only the issued original is ever served to a customer or compared by the public file-check. **`pdf_sha256` is taken over the final stored bytes of the issued file, including any embedded signature** — the checksum is computed after signing, not before, so the weekly job re-computes the same value for the life of the record. Issued report files are marked immutable and the file permissions are set read-only. **The backup procedure must cover the file store and the database together, and the restore drill must verify a report PDF opens after restore.** | [MUST] |
| **DB-15** | **State machines.** Each transaction table holds `state VARCHAR(30) NOT NULL`, `state_changed_at TIMESTAMPTZ`, `state_changed_by_user_id`. Allowed moves live in `sys_state_transition_rule` as data. Every move is executed by **one service function** which: checks the rule exists, checks the actor's permission, checks a reason where required, checks the "must be a different person" rule where required, updates the state columns, writes a `sys_state_transition` row with the seconds spent in the previous state, and runs the configured side effects. **No screen, controller or report may set a state column directly.** Turnaround, bottleneck and hold-duration reporting all read `sys_state_transition`, never scattered timestamps. | [MUST] |
| **DB-16** | **Multi-unit readiness from day one.** `unit_id BIGINT NOT NULL` appears on every transaction table and on masters that can vary by unit. It forms part of the unique key for every number series. Every query passes through a mandatory unit scope supplied by the session, and a test confirms that a user of one unit cannot read another unit's records even by supplying an identifier directly. There is exactly one narrow exception, for WF-20's inter-unit referral: a row whose `performing_unit_id` or `billing_unit_id` names the session unit is visible to that unit through the **inter-unit referral views only**, which expose the sample identity, test, method, result and price — not the customer identity, the audit trail or the invoice. All other queries remain scoped to `unit_id` alone. The exception is declared as named views rather than as a row predicate, because `txn_observation`, `txn_result`, `txn_verification` and `sys_state_transition` carry no unit column and are reached by join. This costs almost nothing now and is a rewrite later if omitted. | [MUST] |
| **DB-17** | **Time.** All moments are stored as Coordinated Universal Time in `TIMESTAMPTZ` (or `DATETIME(3)` set to UTC). The application timezone is `Asia/Kolkata`, which is UTC plus 5 hours 30 minutes with no daylight saving. Display is always India Standard Time. Calendar dates that are dates in law or in trade — report date, invoice date, calibration due date, expiry date, retention date — are stored as `DATE` in India Standard Time terms, not derived from a UTC timestamp. Every "today" comparison uses the India Standard Time date. | [MUST] |
| **DB-18** | **Money and quantities.** Money is `DECIMAL(14,2)`. Tax percentages are `DECIMAL(6,3)`. Quantities are `DECIMAL(18,6)`. Measured and reported values are `DECIMAL(18,6)`; the full-precision computed value before rounding is `DECIMAL(24,10)`. **Floating-point types are forbidden for money and for reported results**, because they cannot represent decimal values exactly and the same calculation can then give two different answers. Rounding happens **once**, at result finalisation, using the method's stored rounding rule, and both the unrounded and the presented value are stored, with the number of decimals used. | [MUST] |
| **DB-19** | **Storing "less than the detection limit" and "not tested".** `txn_result` holds three related columns: `value_num` (the number, if there is one), `value_text` (a descriptive result such as a grade or "Absent"), and `value_qualifier` from a fixed list: `=` (a plain value), `<` (less than), `>` (greater than), `ND` (not detected), `NT` (not tested), `NP` (not performed), `IS` (insufficient sample), `PRES` / `ABS` (present / absent). Where the qualifier is `<` or `>`, `value_num` holds the limit and `detection_limit` holds the method's limit of detection. Rules: **never store `<0.5` as text in a numeric column** (it stops all averaging and trending); **never store 0 for "not detected"** (it silently corrupts every average, trend and grade calculation); **never leave a not-tested parameter as an empty row that looks like a missing entry** — say so explicitly with `NT` and a reason. Display is generated from the qualifier and the value: "< 0.5 %", "Not detected (limit of detection 0.1 %)", "Not tested". Statistical functions and the grading engine must handle each qualifier explicitly and refuse to guess. | [MUST] |
| **DB-20** | Every result row stores `method_id` **and** `method_revision`, and every observation stores `equipment_id` and, where the method consumes one, `consumable_lot_id` or `prepared_solution_id`. These links are what make the retrospective impact analysis of a failed instrument, a bad reagent lot or a wrongly standardised working solution a single query rather than an impossible manual search, and the prepared-solution path reaches its own source lots through `mst_prepared_solution_source` (M12-32). **They are `NOT NULL` where the method requires them**, and where the method consumes a reagent exactly one of the two consumption columns is set. | [MUST] |
| **DB-21** | Snapshot rules. `txn_sample_test` snapshots the method, its revision, the standard turnaround and the price at the moment the test is created. `txn_report_test.snapshot_json` freezes every value that is printed and, per result, the `txn_result.id` and the `rev_no` that value came from — the revision number is not a printed value, so it must be frozen explicitly or DB-43 has nothing to compare against. `txn_report` snapshots the printed customer name and address. A report reprinted in 2033 must render identically even if the method, the price and the customer's address have all changed since. | [MUST] |
| **DB-22** | Reference data that changes over time is dated, never overwritten: rate cards, tax rates, specification and grade tables, methods, competency authorisations, accredited scope, statements, templates, retention policies. Each has `effective_from` and `effective_to`, and every historical query selects the row in force on the relevant date. Overlapping ranges are refused. | [MUST] |
| **DB-23** | Character encoding is UTF-8 throughout — database, connection, application and PDF — so that Telugu and Devanagari text survives from the screen to the printed report. This is set once, at creation, and verified with real Telugu test data in Phase 1. | [MUST] |
| **DB-24** | The database schema is created and changed only by numbered forward-only migration scripts held in source control (ARC-29). The production schema is never edited by hand. | [MUST] |

### 25.6 The most important integrity rules, as constraints and triggers

These are the rules that stop impossible data from existing at all. Each is implemented in the database, not only in the application, because an application bug or a maintenance script must not be able to break them.

| ID | Rule | How it is enforced |
|---|---|---|
| DB-25 | An issued report cannot be modified, except to set `superseded_by_report_id` and `state`. | Trigger on `txn_report` that raises an error on any other column change where `state` is issued or later. |
| DB-26 | An issued report always has a stored file and a fingerprint. | `CHECK (state <> 'ISSUED' OR (pdf_attachment_id IS NOT NULL AND pdf_sha256 IS NOT NULL))`. |
| DB-27 | A report carrying a Unique Laboratory Report number or the accreditation symbol contains no out-of-scope parameter. | `CHECK ((ulr_no IS NULL AND nabl_symbol_used = false) OR contains_out_of_scope = false)`. |
| DB-28 | A result cannot be verified by the person who submitted it, unless an override with a reason has been recorded. | Trigger on `txn_verification` comparing `actor_personnel_id` with the test's `submitted_by_personnel_id`; an override requires a linked reason and raises a nonconformity. |
| DB-29 | A test cannot move to submitted while any mandatory parameter has no result row. | Trigger on the state transition, called from the single transition function. |
| DB-30 | An observation cannot be recorded against equipment whose calibration or intermediate check had expired at `observed_at`. | Trigger comparing `observed_at` against the equipment's valid-until dates; an override requires an authorised user, a reason, and raises a nonconformity. |
| DB-31 | An observation cannot consume a consumable lot that was expired, rejected or unapproved at `observed_at`. | Trigger with the same override pattern. |
| DB-32 | An observation cannot be recorded by a person without a valid authorisation for that method and the "perform" activity on `observed_at`. | Trigger against `mst_competency`; same override pattern. |
| DB-33 | A raw observation row can never be updated or deleted; a correction is a new row. | No UPDATE or DELETE permission on `txn_observation` for the application login, except a single permitted update setting `is_excluded` with a reason. |
| DB-34 | Exactly one current result exists per test and parameter. | Partial unique index on `(sample_test_id, parameter_id)` where `is_current` is true. |
| DB-35 | A number series never issues the same number twice for a unit, document type and period. | Unique constraint on the resulting document number column, plus the locked-counter allocation of DB-08. |
| DB-36 | An invoice cannot be cancelled after the return period in which it was reported has been filed; the correction must be a credit note. | Trigger comparing `doc_date` against the filed-up-to date, which is held per tax registration and per return period in `sys_setting` (scope `gst_registration`, key `returns_filed_upto`), not as a single column on `mst_gst_registration`. |

## 26. Implementation plan and phasing

**Assumption for every effort figure: one full-time developer, working alone, five days a week.** Figures are in developer-weeks and include design, coding, automated tests, the developer's own testing, and writing the documentation for that phase. They do **not** include the laboratory's user acceptance testing time, which runs in parallel and needs the laboratory's people, not the developer's.

If the developer is part-time, multiply the calendar duration accordingly and do not compress the phases — the sequence matters more than the speed.

| **1** | Replace the paper sample register end to end, from the reviewed Test Request to a signed report with a QR code, including the conditioned-mass certificate of the conditioning module (M10), the equipment, lot, competency and environment capture that gates a result, and report amendment and withdrawal | 32–38 | 34–40 |

Roughly **fifteen to eighteen months of one person's full time** to a complete system, with the paper sample register replaced somewhere in **month eight or nine**.

**How to read these figures, honestly.** They are ranges, not commitments, and the range is the point: a solo developer building around twenty-five dated master tables, a data-driven state machine, a field-level trigger audit trail, an author-it-yourself calculation and grading engine, tagged and signed PDFs with Indic text, a separately hosted accessible verification service, four manuals and the ISO/IEC 17025 clause 7.11.2 validation package cannot be costed to the week. The figures **exclude** leave and public holidays, the defect-fix cycles that follow each user acceptance test, and the laboratory's own master-data work (the test catalogue of PLN-08, the specification and grade tables, the rate cards, the equipment and competency records) — that work is owned by the laboratory and runs on its own clock. Three items carry most of the schedule risk and should be attacked first, inside Phase 1, not left to the end: (a) the tagged and digitally signed PDF with correct Telugu and Devanagari shaping — the library choice is now made and tested (§24.4), but the structure tree is hand-built, so the very first template must be written tag-first and no later pass can retrofit it (NFR-70, NFR-93, ARC-17, PLN-28); (b) the calculation and grading engine a non-programmer must be able to author (NFR-109, AC-38); and (c) the trigger-written audit trail with the revoked-DELETE grant model (DB-04, DB-05, NFR-43), which must be in continuous integration from day one because retrofitting it across forty tables is not practical.

Phase 1 is large because it is the release that goes live, and everything an issued certificate depends on has to be inside it. It is delivered in internal increments in this order — masters, then intake and acceptance against a reviewed request, then the bench with its equipment, lot, competency and environment gates, then verification, then the report with its amendment and withdrawal paths — but it has **one** go-live, one acceptance milestone and one cut-over, described in §26.3.

| **PLN-28** | **The Indic text and tagged-PDF acceptance test. It renders a single page carrying ప్రయోగశాల, శ్రీ ధర్మవరం, కీర్తి, మూర్తి, ప్రు, పట్టు and केंद्रीय रेशम बोर्ड — English, Telugu and Devanagari together on one page, because that is what an issued certificate carries, and a test page carrying only one script hides a whole class of defect — and asserts four things: that rendering throws no exception; that the glyph identifiers and advances written into the page's content stream are exactly what harfbuzzjs returns for the same string in the same font, held as a golden file so that a change in shaping is visible rather than silent; that every one of those strings is found, in logical order, by a plain text search of the text extracted back out of the finished file; and that `veraPDF -f ua1` passes that file with no failed rule. It then applies the digital signature to the same file and runs all four assertions again against the signed file, adding a check that the signature's byte range still covers the whole document. Signing is an **incremental update**: it appends to the file rather than rewriting it, so a validator run made before signing says nothing about the document a customer actually receives, and only the signed run is evidence. **The measured result, on the built document component: veraPDF 1.30.2, profile ua1, 106 of 106 rules, `isCompliant="true"` — unsigned and signed alike.** The reason this test stays in the build for the life of the system is recorded here, where a developer looking to make the build faster will read it. This specification, following the wider literature, carried the claim that the layout library passes PDF/UA-1. Run against our own document it did not: it failed four rules across twenty-five checks, and repairing those four exposed two further failures that are only reachable once the first four are gone. Six defects, then, sat between a document that already had a complete structure tree, correct `/ActualText` and byte-perfect shaping — everything ARC-47 asks for, checked in the emitted file rather than assumed — and a document that actually conforms. Not one of the six shows on the printed page, and not one of them was going to be found by reading the code; they were found by running the validator over a file everybody believed was finished. Each is now recorded as its own requirement in §24.4 and is not restated here; one of them is ARC-49, which this run confirms is real and whose workaround it confirms works. The default shaping engine **throws** on ordinary Telugu rather than mis-setting it, so the failure is a crashed report, not an ugly one — which is why the shaping engine is a named, deliberate choice in §24.4 rather than whatever the layout library ships with. The text layer is built after shaping and so comes out in **visual** rather than logical order, which leaves the certificate unsearchable, uncopyable and read aloud in the wrong character order — the substance of NFR-70 and NFR-93, not a cosmetic detail — and no accessibility validator detects it. And a font-subset side table that the format does not require can fail validation for one typeface while another passes, so the build looks healthy until somebody changes the font. This one test is also the only thing that will catch any of these coming back from a dependency upgrade in five years' time, made by someone who is not this developer. Pin the exact versions it was written against — pdfkit 0.19.1, harfbuzzjs 1.6.0 and veraPDF 1.30.2 — name them beside the test, and vendor them offline per ARC-16. **The validator is a build-machine tool and belongs nowhere else** — the development machine and the ARC-30 continuous integration job, never the laboratory server, for the reason ARC-53 records. It cost about a day, inside PLN-09's setup week. [MUST] |

### 26.7 Phase 5 — Outward facing (6–8 weeks)

**Included:** the customer portal (status, past reports, invoices, a new request, a share-for-verification link with expiry and an access log); notifications by in-application message, email and SMS with templates in English and Telugu and a delivery log; the escalation ladder for overdue work; dashboards with no more than eight tiles; the analytics reports of §8 of the research brief — turnaround performance, bottleneck dwell time, first-time-right, rejection analysis, revenue per test and per customer, grade distribution by district and season, equipment utilisation; the retention and disposal register; the audit-trail extract; hardening of the public verification service, its accessibility conformance evidence, and its security review.

**What the laboratory can do at the end:** stop answering the telephone about status; see where the days actually go; and give headquarters trend data nobody could produce before.

**Acceptance milestone:** a real customer tracks a real sample and downloads a real report without telephoning the laboratory; and the accessibility and security reviews of the public page are closed.

**Risk if skipped:** the counter stays a call centre, and the genuine research value in five years of grade distributions by reeler and district is never realised.

---

### 26.8 Phase 6 — Depth (5–7 weeks)

**Included:** instrument file import by watched folder, with a per-instrument mapping held as configuration, the raw file kept forever as an attachment with its fingerprint, and unmatched rows quarantined for a person; balance capture over a serial-to-USB adapter for high-volume weighing; worksheets and run sheets with quality-control positions; subcontracting with the customer's recorded approval and the identification of external results on the report; the stronger digital signature (an organisational Document Signer certificate on a hardware security module, swapped in behind the ARC-17 signing interface in place of the development key file, and producing a basic valid PAdES signature — **not** long-term validation, which the OPEN-Q-T31 default puts out of scope, and which if it is ever required arrives as a replacement signing implementation rather than as an addition to this one); the section 63 evidence certificate generator; the machine-readable report file alongside the PDF, so that a later DigiLocker onboarding is a configuration exercise rather than a rebuild; and second-unit readiness testing.

**Acceptance milestone:** 100 balance readings arrive from the instrument's own file with no typing, and the resulting report validates as digitally signed in an ordinary PDF reader with its tagged structure still intact after signing.

**Risk if skipped:** none that is urgent. **This is deliberately last.** Laboratories that begin with instrument interfacing spend the whole budget on three instruments and never ship the workflow. Many of this unit's tests — seriplane evenness, cleanness and neatness, cohesion counting, visual and tactual examination — are judgement against standard photographs with no digital output at all, so structured manual entry is the correct model for a large share of the work, not a compromise.

## 27. Acceptance criteria and test scenarios

These are the tests that decide whether the system is accepted. Each is tagged with who runs it: **[LAB]** a member of the laboratory staff, unaided, following the scenario as written; **[DEV+LAB]** the developer sets up or operates the technical step while a named laboratory officer observes and signs the result; **[DEV]** the developer runs it and files a written test report that the Unit Incharge signs. The tags follow the allocation in §26.12. Only the criteria that need the developer carry a tag in the identifier column; **every untagged criterion is [LAB]**. Every one must be recorded as passed, failed, or passed-with-observation, and the completed set forms part of the software validation package required by ISO/IEC 17025 clause 7.11.2.

**Note on the "Verifies" column.** Where a requirement belongs to this section it is given by its identifier (NFR-, ARC-, DB-, PLN-). Where it belongs to a functional section written elsewhere in this document, the module is named in words rather than guessed at by number, so that the identifiers in this table are always correct.

## 29. What this buys the lab (benefits, in the scientist's terms)

| # | Today | With the system |
|---|---|---|
| 1 | A sample is written into a bound register by hand; the same customer's name is written again on the worksheet, again on the report, and again on the bill. | The sample is entered once at the counter, and every later document draws on that one entry, so a mistake cannot be introduced by copying. |
| 2 | Finding last year's report for a customer who has lost his copy means going through the register and the file cabinet. | Any report from the last seven years is found by typing the report number, the customer's name, the bale mark, or a date range, and reprinted marked "duplicate copy". |
| 3 | If a tester is on leave, only he knows how far his samples have got. | Every sample's exact stage, its tester, and whether it is late is on one screen that the Unit Incharge can see at any time. |
| 4 | Twenty skein weights are written on a slip of paper, the average and deviation are worked out by hand or on a calculator, and the slip is filed. | The twenty readings are typed straight in, the average, deviation and grade are computed the same way every time, and the readings themselves are kept for ever and can be shown to anyone who questions the result. |
| 5 | A customer asking "is my report ready?" is answered by walking to the bench. | The customer can see the stage himself, and is sent a message when the report is issued. |
| 6 | The monthly return to CSTRI headquarters is typed out from the registers, taking most of a day, and the figures depend on who added them up. | The monthly return is produced in one action, from the same records the work was done in, and a copy of exactly what was sent is kept so a later correction cannot quietly change it. |
| 7 | A buyer in the market has no way to tell a genuine certificate from a photocopy with the numbers changed. | The buyer scans the code on the certificate with an ordinary phone and is told, on the laboratory's own page, whether that report is genuine, and whether it has since been amended or cancelled. |
| 8 | If a report has to be corrected, the practical choices are to re-type it with the same number, or to write a letter. | A correction is issued as a proper amended or replacement report, stating what changed and why, referring to the original, and the original stays on record marked as superseded — including on the verification page. |
| 9 | A balance found out of calibration means someone must guess which results were affected, from memory and the register. | The system lists every test, every sample and every issued report that used that balance since its last good check, in one action, and records what was decided about each. |
| 10 | An expired reagent or an out-of-calibration instrument can be used by accident, and nobody knows until much later. | The system refuses to accept the result, names the reason, and if an authorised person overrides it, records who did so and why. |
| 11 | Who is competent to run which method lives in a file and in the Unit Incharge's head. | The system will not let a result be entered, checked, verified or signed by someone who is not authorised for that method on that date, and can answer "who was authorised in March last year?" |
| 12 | The tester who is testing a well-known trader's silk knows whose it is. | The tester sees the sample number, the material, the declared denier and the test — and not the customer's name, address or price; if he needs to know, he asks, and that request is recorded. |
| 13 | Whether the unit met its two-to-three-day service standard is a matter of impression. | The system reports, for each test, how long it actually took, how much of that was waiting for a payment or a clarification, and which stage the days were spent in. |
| 14 | Which tests earn money and which consume time for thirty rupees is not known in any usable form. | Revenue per test, per customer and per month comes out of the same records, which is the evidence needed when asking headquarters to revise a rate or buy an instrument. |
| 15 | Five years of denier and grade results sit in registers where nobody can look at them together. | Grade distribution by district, by reeling technology and by season becomes a report — which is research output the unit is already expected to produce and currently cannot. |
| 16 | An assessor's questions are answered by fetching files, and some answers take a day. | Most assessor questions — the calibration status on a given date, who signed what, what changed and why, the complete history of one sample — are answered from the screen while he watches. |

### What this system will **not** fix

It will not make a tensile test faster. The oven still takes its time, the twenty-four-hour conditioning is still twenty-four hours, and a seriplane panel still has to be looked at by a person against the standard photographs. The gains are in the time around the testing — the writing, the copying, the searching, the totalling and the explaining — not in the testing itself.

It will not remove the need for discipline. If a reading is written down wrongly, the system will faithfully compute the wrong average; if a reason for a change is typed as "correction", the audit trail will say "correction" and mean nothing. The system makes carelessness visible and traceable, which is genuinely valuable, but it does not make it harmless.

It will not run itself. It needs **one named person in the unit who owns the master data** — the test catalogue, the methods, the parameters, the grade tables, the rate card, the holiday list — and who keeps them right. That person does not need to be a programmer, but they do need to care, and they need a trained deputy for when they are transferred. A laboratory system whose reference data has gone stale is worse than a register, because a register never pretends to be current.
